# Use one host-probe module for setup, doctor, and refresh

OKF Harness answers "is this executable on the host" once, from one host-probe module beside verification.ts, for universal setup, doctor, and refresh guidance. The four drifted executable-lookup and probe implementations (setup, doctor, refresh, agent-pack) converged into one module: a single executable-candidate policy (bare command name first, then PATHEXT variants and X_OK), probe orchestration with an injected runner, one Windows shell invocation strategy, one shadowing and global-version detection, and shared command-error readers. Consumers keep only presentation, and the unification fixes two behavior bugs in the same move: refresh guidance missed bare win32 names, and doctor's `.cmd` probes ran without a working directory. The consuming surfaces shrink by net roughly 300 lines; the new module and its tests add back the remainder.

One lookup policy answers the same question in every surface, so setup and doctor cannot disagree about a machine: a host executable is found or not found identically whether a person runs universal setup, asks doctor about the machine, or follows refresh guidance.

This record clarifies what the Agent Plugin convergence records mean when they say setup and doctor are unchanged or not modified (ADR 0050, ADR 0051): the claim covers their install surfaces, their installable host set, and the ADR 0044 and ADR 0045 mechanisms — the portable target renders, it never installs. Executable lookup itself is shared through this module, whose creation preceded that convergence, so a reader comparing the ADRs against the repository history finds no contradiction.

The cost accepted is that one lookup policy must serve three surfaces with different call shapes — synchronous probing with an injected runner, and an async boolean form for refresh guidance against an explicit runtime platform — so the shared policy is exercised through both shapes rather than a single entry point.
